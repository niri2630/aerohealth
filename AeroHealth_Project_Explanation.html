1. Executive Summary

AeroHealth is a two-part application consisting of a FastAPI backend and a React/TanStack frontend. The product presents air-quality readings, a personal risk score, predicted health impacts, SHAP explanations, AQI-aware routes, educational material, reports, and an AI assistant.

The system is currently a functional prototype. Its model is trained on synthetic data, historical readings are generated rather than stored in a time-series database, route AQI is estimated synthetically, and the reports page uses mock data. These choices make the demo self-contained but are not substitutes for clinical validation or production environmental data.

User -> React dashboard -> AQI / prediction / SHAP / route / history REST APIs -> OpenAQ, XGBoost + SHAP, OpenStreetMap/OSMnx, Nominatim -> visual panels, map, risk gauge, assistant, reports

2. Repository Structure

Backend

Frontend

Generated and cached assets

graph_cache stores downloaded graphs by rounded location.

cache directories contain cached data files.

Virtual environments contain installed Python packages and are not application source.

Utility launcher

The outer main.py is a graph-generation utility. It downloads a road graph around Sahyadri College or Adyar, adds speed/travel-time data, saves demo_graph.pickle, and verifies that a route exists.

3. Backend Architecture

Startup lifecycle

  1. FastAPI creates the application and enables open CORS for the demo.
  2. The startup hook trains the synthetic XGBoost model.
  3. A SHAP TreeExplainer is initialized.
  4. The pre-downloaded road graph is loaded when available.
  5. A prediction and explanation are run once to reduce first-request latency.
  6. /health reports model, graph, and warm-up status.

Dependencies

The backend dependencies are listed in aerohealth-api/requirements.txt: FastAPI, Uvicorn, httpx, XGBoost, SHAP, NumPy, NetworkX, OSMnx, scikit-learn, Pydantic, OpenAI, and python-dotenv.

5. AQI Data Pipeline

aqi.py rounds coordinates to three decimals and stores the response for five minutes. It searches OpenAQ v3 within a 25 km radius, selects the nearest station, fetches latest measurements, and maps parameters such as PM2.5, PM10, NO2, O3, and SO2 into the frontend contract.

AQI is estimated from PM2.5 through simplified breakpoints ranging from 0 to 500. Temperature and humidity use defaults when the station does not provide them.

Fallback chain: requested OpenAQ location -> verified Adyar/Mangaluru coordinates -> deterministic synthetic reading. The UI can therefore remain populated even without a working external API.

6. Risk Model and Explainability

Features

The model uses PM2.5, NO2, O3, SO2, temperature, humidity, heart rate, age, weight, and asthma status.

Training

At startup, 5,000 synthetic rows are sampled across plausible pollution and biometric ranges. A hand-written formula combines pollutant normalization, heart rate, age, weight, asthma, and humidity effects. Gaussian noise is added, and the result is clipped to 0-100. XGBoost learns this synthetic relationship.

Outputs

OutputMeaning
risk_scoreInteger score from 0 to 100.
risk_labelLow, Moderate, High, or Severe using fixed thresholds.
heart_rate_deltaEstimated increase based on score.
hrv_deltaEstimated HRV decrease based on score.
resp_stress_deltaEstimated respiratory stress increase.

SHAP

SHAP calculates how each feature moves the prediction away from the model's base value. Positive values raise risk and negative values lower risk. The frontend sorts and animates the largest contributions first, making the prediction more interpretable.

Important: this is an educational/demo risk indicator, not a medical diagnosis or clinically validated prediction system.

7. Route Planning

routing.py works with NetworkX MultiDiGraphs created by OSMnx. Graphs are checked in memory, then on disk, then downloaded on demand around the route midpoint.

The direct path minimizes road length. For the safe path, every edge receives an AQI estimate and an adjusted weight:

aqi_weighted = length * (1 + (aqi / 100) * LAMBDA)
LAMBDA = 2.5

The algorithm also selects a midpoint waypoint nudged perpendicular to the direct path, choosing the side with lower estimated pollution. It calculates two AQI-weighted legs through that waypoint. If the safe route collapses to the direct route, it tries removing the dirtiest direct edge. If graph loading or path calculation fails, a hard-coded smooth demo route is returned.

8. Frontend Pages and User Flows

Dashboard: /

The dashboard begins with a short boot sequence, then loads the current AQI and history. Pollutants are combined with user vitals and sent to the prediction and explanation endpoints. The main interface contains the risk gauge, telemetry, map, health-impact controls, and SHAP panel.

React Query caches requests. AQI refreshes every two minutes. Vital changes are debounced by 320 ms so slider movement does not generate a request for every pixel of motion.

Location selection

TopNav.tsx provides preset cities and a command-style search interface. Searches are geocoded through the backend. Regional aliases and Karnataka-specific scoring improve results for locations around Mangaluru and Udupi.

Map workflow

  1. User enters or accepts an origin and destination.
  2. Addresses are geocoded if necessary.
  3. The frontend requests a route.
  4. If the road graph is downloading, the frontend polls status every two seconds.
  5. When ready, the direct and safe GeoJSON lines are displayed on Leaflet.
  6. Route metrics are converted into a route-specific risk estimate.

AI assistant: /assistant

The assistant stores multiple conversations in browser storage and supports streaming chat, speech recognition, text-to-speech, image generation, and contextual prompts. It currently uses the frontend Puter SDK with Grok rather than the backend /api/chat endpoint.

Reports: /reports

The reports screen shows summary statistics, insights, recommendations, and exposure history. These values are currently hard-coded demo values. The export action simulates a delay and displays an alert; it does not yet produce a PDF.

Learn: /learn

The learning screen is static educational content covering PM2.5, PM10, NO2, O3, SO2, CO, AQI bands, health effects, and protective actions.

9. Frontend Data Resilience

The API layer in src/lib/aero/api.ts wraps REST calls with withFallback. If the API URL is missing or a request fails, deterministic local implementations generate plausible values for AQI, prediction, SHAP, routes, and history.

The result includes a simulated flag. The dashboard uses this flag to show that the displayed signal is local simulation rather than live backend data.

This approach improves the judging/demo experience but can conceal backend connectivity problems unless the simulated indicator is noticed.

10. Visual and Interaction Design

  • Dark, instrument-style interface with a teal primary accent.
  • Monospace typography for telemetry values and coordinates.
  • Animated risk gauge with risk-dependent colors.
  • Glass-like panels with subtle borders and ambient glow.
  • Animated grid, scanline, and background drift effects.
  • Staggered panel entrances and count-up numeric transitions.
  • Animated SHAP bars and route-line drawing.
  • Reduced-motion handling through Motion's reduced-motion support.

The shared components are in src/components/aero. General primitives include Panel, PanelHead, CountUp, Shimmer, and CalmState.

11. Configuration and Running

Backend

cd aerohealth-api
python -m uvicorn main:app --reload --port 8000

The backend reads XAI_API_KEY from the environment for its optional Grok integration.

Frontend

cd aerohealth-interface-frontend
npm install
npm run dev

The frontend reads the backend URL from VITE_API_URL, for example:

VITE_API_URL=http://localhost:8000

Other scripts are npm run build, npm run preview, npm run lint, and npm run format.

13. Final Assessment

AeroHealth is a thoughtfully integrated prototype rather than a collection of isolated screens. Its strongest aspect is the complete user journey: observe air quality, personalize with vitals, understand why the score changed, compare safer travel options, and ask an assistant for an explanation.

The main technical boundary is between demonstration logic and production evidence. The UI and API contracts are well defined, but model outputs, historical trends, route pollution, and reports must be connected to validated sources before the system can be treated as a real health product.
